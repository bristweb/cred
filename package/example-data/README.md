# Example data (fictional)

The **examples** that ship with [bristweb/cred](https://github.com/bristweb/cred): sample content for an invented bike shop, not a real business. Do not present it as real reviews or testimonials.

Everything here is example content by location, so nothing is tagged `example: true`. `include_examples` in `config.js` (default `true`) shows it; set it to `false` to leave all of it out of the published widget without deleting any file. Once you copy files into your own `data/`, they are your content. Keep this folder untouched in a fork so upstream updates merge cleanly, and put your own data in a copy of it in `data/`. See [Fork and replace](https://github.com/bristweb/cred#fork-and-replace).

Demo platforms: **Google**, **Yelp**, and **Facebook** (common review sources). The business and review text are fictional; the platform names identify where each sample would appear.

In a fork, copy the files of this folder into `data/` (empty upstream) and replace them with yours. With no `data-source`, the widget reads `/data/` once it has a `config.js`, and these examples until then. Or copy it to start a separate data repo; then add a `_headers` (CORS, see below) and an empty `.nojekyll` at that repo's root and copy the sample workflows from [`docs/data-repo-workflows/`](../../docs/data-repo-workflows/) to `.github/workflows/`.

## Publish

**Hosting a separate data repo.** (A fork publishes through its own workflows instead, see the main README.) Recommended: Cloudflare Pages. The sample `docs/data-repo-workflows/deploy.yml` (copied to `.github/workflows/`) publishes the repo root on every push to `main` once you add three repo secrets: `CLOUDFLARE_API_TOKEN` (Pages edit permission), `CLOUDFLARE_ACCOUNT_ID` and `CF_PAGES_PROJECT` (project name; create it once in the Cloudflare dashboard as a Direct Upload project). A root `_headers` with `/*` and `Access-Control-Allow-Origin: *` opens CORS. Backup: GitHub Pages needs no extra files; in Settings → Pages choose *Deploy from a branch*, `main`, `/ (root)` (with an empty `.nojekyll` at the root).

Then point the widget at the published URL (`data-source` is only needed when this folder is served from a different site than the script; in a fork that holds both, omit it and the widget reads `/data/` if it has a `config.js`, or these examples (`package/example-data/`) if not):

```html
<script src="https://cred.bristleconeweb.com/assets/js/cred.js"
        data-source="https://YOUR_DATA_REPO.pages.dev/" defer></script>
```

Google Sites / fixed-height box: add `data-constrained="true"`.

## Layout

- `config.js` (with `cred-config.d.ts` for editor type hints) — `include_examples`, business, platforms, display, summary, optional `accolades` / `testimonials`, `reviews.years` (optional `languages` / `defaultLanguage`)
- `lang/` — optional UI wording listed in `languages` (partial OK; widget ships English)
- `reviews/<year>.json` — review records
- `theme/theme.css` — `--rw-*` colors (light + dark)
- `assets/` — local files, sorted by kind: `icons/` (platform logos, award and credential badges, company marks), `images/` (photos, posters; `images/reviewers/` for avatars), `video/`, `audio/`, and `ATTRIBUTION.md`
- `badge.json`, `badge.svg`, `cred-config.d.ts` — generated by `node package/tools/badge.mjs` and `npm run schemas`

This folder mirrors the `data/` layout a client creates; see [`../../data/README.md`](../../data/README.md). Sample workflows for a standalone data repo are in [`docs/data-repo-workflows/`](../../docs/data-repo-workflows/).
