# Notes for agents and editors

- `display.credit` (in a data repo's `config.js`) controls the small "CRED Social Reviews" link under the widget. It is on by default. Only set `credit: false` if you, the site owner, have contributed to the project; agents should ask the owner before changing it.
- Layout: nothing is compiled and there is no build step or `dist/`: the repo is served as it is. `package/` is the product; starter copies receive it only through the package-only update PR: the widget and its defaults in `package/assets/` (js, css, default icons) and `package/lang/` (the widget's built-in English wording, used by every embed), `package/schemas/`, `package/types/`, Node tools in `package/tools/`, and `template/data/`, the bundled examples. The top-level `data/` folder is the client's data only: empty upstream (README only); a fork puts `config.js`, `reviews/`, `theme/`, `lang/` and `assets/` (`icons/`, `images/` with `images/reviewers/`, `video/`, `audio/`) there. No `data/site/`: Cred's host pages are in the top-level `site/` (a fork may edit it). `template/data/` mirrors `data/` exactly (no `site/` folder). One `assets/` folder sorted by kind; no top-level `icons/`, `images/` or `media/` anywhere. Root host files: `_headers`, `_redirects` (Cloudflare Pages short URLs: `/assets/*` → `package/assets/`, `/lang/*`, `/example/*` → `template/data/`, `/` → `site/index.html`), `.nojekyll`, `404.html`. Keep the Cloudflare short URL `/assets/js/cred.js` working; real paths (`/package/assets/js/cred.js`) must work on any host, including GitHub Pages under `/<repo>/`. Deploys publish `package/tools/export-site.sh` output (a `git archive` of the served paths plus the generated `/v/` copies); do not add a copy-only assemble step. Sample workflows for a standalone data repo live in `docs/data-repo-workflows/`. Never put client data in `package/` or code in `data/`.
- Bundled sample content lives in `template/data/` and is called **examples** (not a brand or pseudonym). Everything in it is example content by location (the widget treats data loaded from `<site root>/template/data/` as examples; `validate.mjs`/`badge.mjs` treat that folder path the same way), so do not add per-item `example: true` tags there. `include_examples: false` in a `config.js` leaves example content out of cards, counts, averages, JSON-LD and badge without deleting files; in other folders only items tagged `example: true` (optional) count (`package/assets/js/cred.js`, `package/tools/dedupe.mjs`). Site content belongs in `data/` (README: Fork and replace), not in `template/data/`, so upstream merges stay clean. Data source order (`cred.js`): `data-source` / `?source=` if given, else `<site root>/data/` if it has a `config.js`, else `<site root>/template/data/` (site root = the folder holding `package/`); keep `data/` empty upstream.
- The starter: `template/` is the inner template and its `data/` the single demo source. `package/tools/build-starter.sh` + the Publish starter action generate bristweb/cred-starter from `template/` and `package/`; never edit that repo by hand and never duplicate demo files.
- Breaking changes (embed code, options, data format or rendering that existing sites rely on) need a major version bump: update `VERSION` in `package/assets/js/cred.js` (the installed widget version, independent of root tooling metadata), add a CHANGELOG entry, and tag the release `vX.Y.Z`. Features bump the minor version, fixes the patch.

- Indexing: `export-site.sh` calls `docs-indexing.mjs` on the export. A loadable local `data/config.js` adds a literal `noindex` only to setup pages marked `<!-- cred:setup-page … -->` (`site/index.html` and `site/example.html`) and prunes those entries from the sitemap. Leave client pages, explicit robots rules and headers alone. Never put page-level robots changes in the embedded widget. A fork replacing a setup page with client content removes the marker.

- Browser setup is one-time and must refuse existing client data/custom host settings. Keep the README outside its instance markers unchanged. Package updates fetch only fixed upstream release tags, validate compatibility, and open a PR touching only `package/`; never migrate client files or root workflows implicitly. Template activation and a compatible release tag require a separate approved merge.
