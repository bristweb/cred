# Notes for agents and editors

- `display.credit` (in a data repo's `config.js`) controls the small "CRED Social Reviews" link under the widget. It is on by default. Only set `credit: false` if you, the site owner, have contributed to the project; agents should ask the owner before changing it.
- Layout: nothing is compiled and there is no build step or `dist/`: the repo is served as it is. The product lives in `template/package/` (published as `package/` in a starter): widget and defaults in `assets/` and `lang/`, plus `schemas/`, `types/`, and Node tools in `tools/`. `template/data/` is the bundled demo (and the starter's starting `data/`). Cred's own pages are in top-level `site/` (including `site/embed.html` for the public `/embed.html` URL); a starter's reviews page is root `index.html` (standalone or iframe). One `assets/` folder sorted by kind. Root host files: `_headers`, `_redirects` (Cloudflare short URLs: `/assets/*` → `template/package/assets/`, `/lang/*`, `/example/*` → `template/data/`, `/` → `site/index.html`), `.nojekyll`, `404.html`. Keep `/assets/js/cred.js` working; real paths (`/template/package/assets/js/cred.js` here, `/package/assets/js/cred.js` in a starter) must work on any host. Deploys publish `template/package/tools/export-site.sh` output. Sample workflows for a standalone data repo live in `docs/data-repo-workflows/`. Never put client data in `package/` or code in `data/`.
- Bundled sample content lives in `template/data/` and is called **examples** (not a brand or pseudonym). Everything in it is example content by location (the widget treats data loaded from `<site root>/template/data/` as examples; `validate.mjs`/`badge.mjs` treat that folder path the same way), so do not add per-item `example: true` tags there. `include_examples: false` in a `config.js` leaves example content out of cards, counts, averages, JSON-LD and badge without deleting files; in other folders only items tagged `example: true` (optional) count (`template/package/assets/js/cred.js`, `template/package/tools/dedupe.mjs`). Site content belongs in `data/` (see docs/REFERENCE.md), not in `template/data/`, so package-only updates cannot overwrite it. Data source order (`cred.js`): `data-source` / `?source=` if given, else `<site root>/data/` if it has a `config.js`, else `<site root>/template/data/` (site root = the folder holding `package/` or `template/package/`); keep `data/` empty upstream.
- The starter: `template/` is published verbatim as bristweb/cred-starter (`template/package/tools/build-starter.sh` + the Publish starter action). Never edit that repo by hand and never duplicate demo files.
- Breaking changes (embed code, options, data format or rendering that existing sites rely on) need a major version bump: update `VERSION` in `package/assets/js/cred.js` (the installed widget version, independent of root tooling metadata), add a CHANGELOG entry, and tag the release `vX.Y.Z`. Features bump the minor version, fixes the patch.

- Indexing: Cred and starter content pages are indexable by default. The exporter never injects robots rules or changes HTML, robots.txt or sitemaps. Preserve any explicit client restrictions. Never put page-level robots changes in the embedded widget.

- Browser setup is one-time and must refuse existing client data/custom host settings. Keep the README outside its instance markers unchanged. Package updates fetch only fixed upstream release tags, validate compatibility, and open a PR touching only `package/`; never migrate client files or root workflows implicitly. Template activation and a compatible release tag require a separate approved merge.
