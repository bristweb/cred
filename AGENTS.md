# Notes for agents and editors

- `display.credit` (in a data repo's `config.js`) controls the small "CRED Social Reviews" link under the widget. It is on by default. Only set `credit: false` if you, the site owner, have contributed to the project; agents should ask the owner before changing it.
- Layout: nothing is compiled and there is no build step or `dist/`: the repo is served as it is. `package/` is the product and forks leave it alone: the widget and its defaults in `package/assets/` (js, css, default icons) and `package/lang/` (the widget's built-in English wording, used by every embed), `package/schemas/`, `package/types/`, Node tools in `package/tools/`, and `package/example-data/`, the bundled examples. The top-level `data/` folder is the client's data only: empty upstream (README only); a fork puts `config.js`, `reviews/`, `theme/`, `lang/` and `assets/` (`icons/`, `images/` with `images/reviewers/`, `video/`, `audio/`) there. No `data/site/`: Cred's host pages are in the top-level `site/` (a fork may edit it). `package/example-data/` mirrors `data/` exactly (no `site/` folder). One `assets/` folder sorted by kind; no top-level `icons/`, `images/` or `media/` anywhere. Root host files: `_headers`, `_redirects` (Cloudflare Pages short URLs: `/assets/*` → `package/assets/`, `/lang/*`, `/example/*` → `package/example-data/`, `/` → `site/index.html`), `.nojekyll`, `404.html`. Keep the Cloudflare short URL `/assets/js/cred.js` working; real paths (`/package/assets/js/cred.js`) must work on any host, including GitHub Pages under `/<repo>/`. Deploys publish `package/tools/export-site.sh` output (a `git archive` of the served paths plus the generated `/v/` copies); do not add a copy-only assemble step. Sample workflows for a standalone data repo live in `docs/data-repo-workflows/`. Never put client data in `package/` or code in `data/`.
- Bundled sample content lives in `package/example-data/` and is called **examples** (not a brand or pseudonym). Everything in it is example content by location (the widget treats data loaded from `<site root>/package/example-data/` as examples; `validate.mjs`/`badge.mjs` treat that folder path the same way), so do not add per-item `example: true` tags there. `include_examples: false` in a `config.js` leaves example content out of cards, counts, averages, JSON-LD and badge without deleting files; in other folders only items tagged `example: true` (optional) count (`package/assets/js/cred.js`, `package/tools/dedupe.mjs`). Site content belongs in `data/` (README: Fork and replace), not in `package/example-data/`, so upstream merges stay clean. Data source order (`cred.js`): `data-source` / `?source=` if given, else `<site root>/data/` if it has a `config.js`, else `<site root>/package/example-data/` (site root = the folder holding `package/`); keep `data/` empty upstream.
- Breaking changes (embed code, options, data format or rendering that existing sites rely on) need a major version bump: update `version` in `package.json` and `VERSION` in `package/assets/js/cred.js`, add a CHANGELOG entry, and tag the release `vX.Y.Z`. Features bump the minor version, fixes the patch.
- The data format is defined once in `package/schemas/schemas.mjs` (Zod, a devDependency; never used by the browser widget). `config.schema.json`, `reviews.schema.json`, `package/types/config.d.ts` and `package/example-data/cred-config.d.ts` are generated by `npm run schemas`; do not edit them by hand. Keep objects open (`z.looseObject`) unless a field must reject unknown keys (review `hidden`). Validation only checks; it never rewrites data.
